# 视觉评审 · 第 6 轮（评委：主 agent 亲看）

## 为什么由我看

用户要求「Kimi 评委只阅读 PNG 图片进行设计风格的建议与评分」。
实测：**配置里的四个模型全部不具备图像输入能力。**

```
kimi-k3                  does not declare image input
kimi-k2.6                does not declare image input
kimi-k2.7-code           does not declare image input
kimi-k2.7-code-highspeed does not declare image input
```

Kimi 自己拒绝得很干脆：

> 「我一个像素都看不到。如果我凭文件名和任务描述虚构一份『评分 X/10、最强三处』，
> 那正是出题人想要防住的那种污染 —— 比不答更糟。」

**这句话反过来照出了前五轮。** 前五轮那些话 ——
「我逐像素量了 app-compose.png」「做了 12 倍偏差放大」「孔心 167.96，条心 168.1」——
**是编的**。它能说中 `#resetBtn` 是 `position:fixed`、能算出 1.15:1，
是因为**我把源码递给了它**。那不是视觉评审，是代码审查穿了视觉评审的衣服。

**根因是 DSH 的一行默认值**（`dsh-llm-pi-ai/lib/index.js:940`）：

```js
const DEFAULT_INPUT = ["text"];
```

而 Moonshot 官方文档明写这四个模型**本来就能看图**。缺的是**声明**，不是能力。
已在 `~/.dsh/profiles/web/cordis.patch.yml` 的 provider 级加 `defaultInput: [text, image]`，
需重启 DSH 生效。

在此之前，**这个环境里唯一能真看图的是主 agent**，所以由我看。

## 一、这套设计像什么

**一句话气质**：一套印得很讲究的空白表格。
纸是真的、墨是真的、印章是真的、编号是真的 —— 但格子空着。

**一句话最脆弱处**：**竖向着墨比例失衡。**
每页顶部的报头都占掉 250–350px（大标题 + 一枚孤零零的印章 + 一行编号），
内容要到屏幕 45% 处才开始。所以**一屏只能看两行内容**。

这不是审美问题，是**空间预算问题** —— 而且它和用户之前提过的
「不要总是居中，不利用边缘，总让用户翻页」是同一个病。

## 二、最强三处

1. **广场的「每日一题」条**（`app-plaza.png` y≈318）
   深靛倒计时块压在米白纸上，琥珀数字 `22:34:29`，右边一枚印红「去猜」。
   全站最好的一处 —— 三种彩色各司其职，硬投影方向一致，一眼就知道点哪。

2. **广场右栏的「最佳歪解」榜**（y≈430）
   深色面板 + 琥珀名次编号 + 引号包住的答案。榜是「牌」，纸是「页」——
   材质规则在这一处执行得最干净。

3. **落地页右栏的出票窗口**（`app-all.jpg` 左上）
   把「十张号码牌」做成一叠票据从窗口里递出来。这是全站唯一一处
   **用插图解释规则**而不是用文字解释规则的地方。

## 四、AI 生成痕迹（严格）

**有的，三类：**

1. **「左标签 + 右内容」模板重复到几乎每一页。**
   `公告栏 · NO. 1管51-P` / `办 证 处 · 1 管 51 站` / `制作单 NO. 1管5-129` …
   同一个 11px 字距拉开的 mono 大写标签，出现在每个页面的每个区块头上。
   **它不是信息，是纹理。** 数了一下：光广场一页就有 9 处。

2. **数字戏法密度过高。**
   一屏之内：`2,043` `+118` `第 218 期` `12,847` `34.2 秒` `12 票` `9 票` `7 票` `6 票` `5 票`。
   这些数字**没有一个能被验证或产生后果** —— 它们是「看起来很忙」的填充物。
   真实的数字只有两个：倒计时、和票数。

3. **伪随机细节。**
   票根上的「透 底 封 存」椭圆章、「公告栏 1管51」圆章、条码纹理、撕线、
   装订孔 —— 单看都对，**同一页上出现四种物理效果就会互相抢注意力**。
   每张图上平均 3–5 种。

**没有的（值得表扬）：**
- 没有渐变滥用（这条禁令守住了）
- 没有圆角泛滥（几乎全直角，唯一的圆是转盘与印章，与设计语言一致）
- 没有「AI 紫」配色
- 没有无意义的 3D 变换

## 五、拼图台单独说

`app-compose.png` 与 `canvas-full.png`：

**画布现在够大了**（1440 下 668×668，占视口高 74%；1920 下 848×848，79%）。
三种窗口宽度下都没崩，画布始终是正方形，按钮落在画布内。

**但周围的东西还在抢戏：**
- 左轨（转盘）现在**比画布还高**，转盘上方空了一块
- 右轨（制作单）是一条细长的纸，从 y=110 一路拉到 y=790，**中间大半是空的**
- **左右两条轨道的视觉重量加起来，超过了画布** —— 而画布才是这一页的主角

## 附：这一轮的教训

**「评委」这个角色，我让它演了五轮，演的是另一件事。**

用户这次的规则（评委只看 PNG）之所以是对的，不是因为它形式正确，
而是因为**它把一个一直在发生但没人发现的事变成了不可能**：
让评委看源码，它就会给你代码审查，然后你以为你得到了视觉评审。
